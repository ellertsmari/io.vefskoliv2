The short version

You registered, and now you can't log in

That is the app working as designed. Every new account starts as pending, and a pending account can't log in until a teacher approves it.

On the school's site a teacher clicks "Approve". In your own database there is no teacher yet, so nobody can approve you. You fix it by opening the database and changing your own user by hand. That is Part 3, and it takes a minute.

If you already have the project running and only the login is the problem, jump straight to Part 3, step 3. If you are not sure where it goes wrong, start at Part 1 and tick the steps off as you go.

Part 1 Once

Make your own test database

MongoDB Atlas hosts a small database for free. You do these steps in the browser at cloud.mongodb.com. Atlas renames its buttons now and then: if a label here is slightly different on your screen, look for the same idea.

  1. Sign in to Atlas

    Create a free account at mongodb.com/cloud/atlas/register, or sign in if you have one. No credit card is needed.

  2. Create a free cluster

    A cluster is the server your database lives on.

    1. On Project Overview, click Create.
    2. Choose the Free option (also called M0).
    3. Pick any provider and a region close to you. Keep the name Cluster0 or choose your own.
    4. Click Create.

    A project can hold one free cluster. If you already have one, use it: a cluster can hold many databases, and you name yours in step 5.

  3. Create a database user

    Atlas asks for this right after creating the cluster. Fill in Username and Password, then click Create Database User.

    • This is the login your app uses for the database. It is not your Atlas account.
    • Use only letters and numbers in the password. Characters like @, :, / or # break the connection string.
    • Write both down. You need them in step 5.

    Skipped it? Open Database Access in the sidebar (under Security) and add a user there, with read and write access to any database.

  4. Let your computer in

    Atlas only answers computers on its allow list. In the same dialog, click Add My Current IP Address, then Finish and Close.

    Your IP address changes when you move between school, home and a café, and then the app suddenly can't connect. For this test database you can allow every address instead: open Network Access in the sidebar (under Security), add an IP address, and enter 0.0.0.0/0.

    Only the database user and password can then get in. That is fine for a test database. You would not do it for a real one.

  5. Copy the connection string and finish it

    Go to Clusters, click Connect on your cluster, then Drivers. Copy the string it shows. It looks like this:

    mongodb+srv://monika:<db_password>@cluster0.ab1cd.mongodb.net/ ?retryWrites=true&w=majority&appName=Cluster0

    Two things are missing, marked in orange. Fix both:

    1. Replace <db_password> with the password from step 3. The < and > go away too.
    2. Add a name for your database between the / and the ?, for example vefskolinn_dev.

    The finished string:

    mongodb+srv://monika:Sunny4Day2026@cluster0.ab1cd.mongodb.net/vefskolinn_dev?retryWrites=true&w=majority&appName=Cluster0

    You don't create the database anywhere else. It appears by itself the first time the app saves something. Without a name the app still works, but everything lands in a database called test, which is easy to lose track of.

One database each, or one for the team?

Both work. With one each, nobody can break anyone else's data, and you can wipe yours whenever you like. With a shared one, everyone sees the same users and dummy data, and only one person has to do Parts 1, 3 and 4: the others just need the finished connection string.

Part 2 For every new clone

Clone the project and connect it

You do these steps in a terminal. They were tested from a fresh clone, in this order.

  1. Clone your fork and switch to the team branch

    git clone https://github.com/monika-hyperisland/tomonika-hyperisland.git
cd tomonika-hyperisland
git switch dev-hyperisland

    Every command from here on runs inside the tomonika-hyperisland folder.

  2. Check Node, then install

    node -v

    It should say v24 and something. If it is older, install Node 24 from nodejs.org first. Then:

    yarn install --frozen-lockfile

    If the terminal answers yarn: command not found, install yarn once and run the line above again:

    npm install --global yarn

    Don't use npm install for the project itself. It rewrites yarn.lock, and that change then shows up in your pull requests.

  3. Create .env.local

    Make a new file called exactly .env.local in the project folder, next to package.json. It holds the three settings the app can't run without: 

    MONGODB_CONNECTION=paste-your-finished-connection-string-here
AUTH_SECRET=paste-a-generated-secret-here
NEXTAUTH_URL=http://localhost:3000

    For AUTH_SECRET, run this and paste what it prints:

    node -e "console.log(require('crypto').randomBytes(32).toString('base64'))"
    • The file name starts with a dot and has no .txt at the end.
    • No spaces around =, no quotes, each setting on one line.
    • If you also have a file called .env, the values in .env.local win. Keep these three in one place.

    Git ignores this file, so your password stays on your computer. That is exactly why it is not in the clone and you have to make it yourself.

  4. Start the app

    yarn dev

    Open localhost:3000/signin. You should see the SIGN IN form.

    Leave the terminal open and keep an eye on it. Once you use the form in Part 3, this line tells you the database is connected:

    [DB] MongoDB connected successfully

    Changed .env.local? Stop the app with Ctrl + C and run yarn dev again, so it reads the new values.

Part 3 The step most people miss

Register, then approve yourself

Registering only gets you halfway. The account exists, but it is waiting for a teacher, and your database has none. So you become the first teacher, by hand.

  1. Register

    On localhost:3000/signin, click REGISTER, fill in the form and click REGISTER again. The password needs at least 8 characters. Any email works; nothing is sent to it.

    A green message shows for three seconds, and then you are back on the login form:

    The app saysYour account is created. A teacher needs to approve it before you can sign in — you'll get access once that's done.

  2. Try to log in, and expect it to fail

    The app saysYour account is waiting for a teacher to approve it. Try again once they have.

    This is not a bug and you did nothing wrong. It even proves that Parts 1 and 2 worked: the app reached your database and found your account there. Waiting will not help, though. No teacher is coming.

  3. Change your user in the database

    1. In Atlas, open Data Explorer in the sidebar.
    2. Open your database (vefskolinn_dev), then the users collection.
    3. Hover over your user and click the pencil icon.
    4. Click the value of status and change pending to active.
    5. Click the value of role and change user to teacher.
    6. Click Update.
    • status: "active" is what lets you log in.
    • role: "teacher" gives you the teacher pages, so you can approve other accounts and create guides. A student has the role user.
    • Spelling counts: lowercase, no extra spaces.

    No users collection? It appears after the first registration. Refresh Data Explorer. Still missing? Look for a database called test: that is where the data goes when the connection string has no database name.

  4. Log in

    Back on the login form, use the same email and password. You land on the Teacher Dashboard. It is mostly empty, because your database is. Part 4 fixes that.

  5. From now on, approve in the app

    You only edit the database by hand for this first user. When a teammate registers, or you make a second account to try the app as a student, log in as the teacher, open PEOPLE, and click Approve under "Waiting for approval".

    To see what a student sees without a second account, use View as user at the top of the page.

Part 4 Whenever you need it

Let AI fill the database

An empty database makes an empty app: no guides, no students, nothing to click on. Writing test data by hand is slow. Your AI assistant can read the project and write a script that does it for you.

  1. Give your AI assistant this request

    Open the assistant inside the project folder (Claude Code, Cursor, Copilot…) and paste this. Change the numbers to whatever you need.

  2. Check the database name before you say yes

    The script prints the name of the database it is about to change. Make sure it is yours (vefskolinn_dev), then let it run. That one look is the whole safety check.

    You can run it again yourself whenever you want the dummy data back the way it started:

    node team/seed-dummy-data.cjs --yes

  3. Log in as one of the dummy people

    The assistant tells you which accounts it made. Log in as a dummy student to see the student side, and as yourself to see the teacher side.

This database is yours to break

It is a test database, completely separate from the school's live one. Nothing in it is real, and nothing you do in it can reach real students or their work. So:

  • Try things. Edit documents, delete them, ask the AI for stranger data: a student with no returns, a guide with a very long title, fifty students at once.
  • If it turns into a mess, delete the whole database in Data Explorer and start again from Part 3. That takes five minutes.
  • Even a leaked connection string is not a catastrophe here. If one ends up in a commit, a screenshot or a chat, change the database user's password in Atlas (Database Access → Edit), put the new one in .env.local, and carry on.

Do still try not to leak it. Keep keys in .env.local and nowhere else: not in the code, not in a pull request, not in a prompt you share. You are building the habit now, while a mistake costs nothing, so that it is automatic on the day the database is a real one.

The seed script stays with the team

It belongs in team/, like your other team-only tools, and never in a pull request to vefskoliv2. A script that deletes and creates data is useful on your test database and dangerous anywhere else. The git handout shows how team/ works.

Stuck?

Find your message

Messages in the browser come first, then messages in the terminal where yarn dev runs.

"Your account is waiting for a teacher to approve it."

Your account is still pending. Do Part 3, step 3.

I changed the status and it still says "waiting"
  • Did you click Update? Open the document again and check that it says active.
  • Is it spelled active, lowercase, in the field status?
  • Are you looking at the database the app uses? Compare the name in your connection string (between / and ?) with the one in Data Explorer. No name in the string means the app uses test.
"Invalid credentials."

The email or password is wrong, or this account does not exist in the database the app is connected to. Check in Data Explorer that your user is in users. If it isn't, register again.

"User with this email already exists."

You are already registered. Don't register again: go to Part 3, step 3 and approve the account you have.

"Too many registrations from this connection" or "Too many attempts"

The app limits how often one computer can register or try to log in. It is your database, so you can lift the limit: in Data Explorer, open the ratelimits collection and delete the documents in it.

I am logged in but I don't see the teacher pages

Your role is read when you log in. After changing role in the database, log out and log in again.

Terminal: "Please define the MONGODB_CONNECTION environment variable inside .env.local"

The app can't find the setting. Check that the file is called exactly .env.local, sits next to package.json, and that the name before the = is spelled MONGODB_CONNECTION. Then restart yarn dev.

Terminal: "[DB Error] Failed to connect to MongoDB", or the page loads for half a minute and fails

The app found the setting but could not get into the database. The rest of the line tells you which of these it is:

  • authentication failed: the username or password in the connection string is wrong, or <db_password> is still in there.
  • a timeout, or "could not connect to any servers": your IP address is not on the allow list. See Part 1, step 4.
  • the address looks cut off: the password contains a character like @ or /. Give the database user a new password with only letters and numbers.
It worked last month and now it can't connect

Atlas pauses a free cluster that nobody has connected to for 30 days. Open Atlas and resume the cluster. Your data is still there.

None of these

Copy the exact message from the terminal and bring it to class, or paste it to your AI assistant together with what you were doing. Leave the connection string out of what you paste.

Questions? Ask in class.
