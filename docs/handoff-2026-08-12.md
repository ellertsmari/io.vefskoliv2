## Things that will bite whoever picks this up

**Guide data reaches a database through Compass, by hand.** No script is ever run against a
database. `scripts/seed*.mjs` are content records, not runnable steps.

**Every exercise task needs an explicit `_id`.** Mongoose mints subdocument ids on save, but the
collection is imported as raw JSON and nothing generates them there. Without ids every task shares
the id `""`, which collapses answer keying, pooling and grading. Stored attempts key their answers
by these ids, so they must never be regenerated once students have submitted.

**Importing guides means dropping the collection first.** Compass imports by inserting, so existing
`_id`s collide. The `_id`s in the file are the originals, which is what keeps returns and reviews
attached (`Return.guide` and `Review.guide` reference guides by `_id`).

**`typescript` and the QuickJS packages must stay in `serverExternalPackages`** in
`next.config.mjs`. Without it `next build` fails outright: the embedded WebAssembly string breaks
the bundler with "octal escape sequences are not allowed in template strings".

**There is no authoring UI for short-answer or code tasks** — deliberately, since Smári is the only
teacher and these tasks are specific to the Module 3 guides. They are hand-written into the guide
document. `ExerciseEditor` holds them opaque and returns them unchanged on save, so an unrelated
edit cannot destroy them. Verify any new code task by running a reference solution through
`runCodeSubmission` before shipping it; there is no quick way to fix a bad test case in front of a
stuck student.

**Short answers can land in `pending`.** A near miss is held for a teacher rather than marked
wrong. Resolve them on the edit-guide page (`ShortAnswerReviewPanel`) — accepting a phrasing adds
it to the key **and re-grades every stored attempt**, because attempts store the score that drives
the student's grade.
